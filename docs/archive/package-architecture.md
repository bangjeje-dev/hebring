# Package Architecture

Phase 10.2 defines the conceptual architecture for the HEBRING npm package. It establishes what the distributed CSS framework will contain and how consumers should access it.

HEBRING remains CSS-first, framework-agnostic, runtime-JS-free, and entirely independent of any user-specific frontend framework.

---

## 1. Core Principles

> **"HEBRING should be easy to install, easy to consume, and easy to inspect."**
> 
> **"The package should expose the framework, not expose the complexity of the build system."**

---

## 2. Package Purpose

HEBRING's npm package distributes the compiled CSS framework for consumption by frontend projects. It provides a simple, coherent CSS library that does not depend on a specific frontend toolchain (like React, Vue, or Vite) to function.

## 3. Source vs Distribution

The conceptual flow of the package architecture is:

```text
src/
  ↓
[ build process ]
  ↓
dist/
  ↓
npm package / CDN
```

- `src/`: The authoring environment and absolute source of truth.
- `dist/`: Contains generated distribution artifacts (not committed as source).
- Consumers should normally consume the distribution artifacts in `dist/`.
- Generated `dist/` files must **never** become the source of truth.

## 4. Proposed Distribution Artifacts

At minimum, the intended output artifacts for the package are:

```text
dist/
├── hebring.css
└── hebring.min.css
```

- `hebring.css`: The readable distribution CSS. Useful for debugging, reading, and non-minified environments.
- `hebring.min.css`: The minified production distribution CSS. Optimized for final deployment.

*(Note: These files are conceptual for this phase and will be generated by a later build implementation).*

## 5. Single CSS Entry Point

HEBRING's primary consumer-facing CSS entry point will favor a simple experience:

```javascript
import "hebring/dist/hebring.css";
// or equivalent CSS consumption via npm
```

The package will favor one coherent framework distribution rather than a fragmented architecture of multiple component-level packages.

## 6. CDN Target

The readable and minified distribution artifacts in `dist/` must be entirely suitable for direct browser stylesheet consumption through a CDN (e.g., `<link rel="stylesheet" href="https://unpkg.com/hebring/dist/hebring.min.css">`).

## 7. Package Contents

The intended npm package contents conceptually include:
- Distribution CSS (`dist/`)
- Useful source CSS (`src/`) for transparency, debugging, inspection, and learning
- Package metadata (`package.json`)
- License (`LICENSE`)
- Relevant documentation (`README.md`)

**Excluded from the package:**
- Tests (unless there is a deliberate reason)
- Scratch files
- Development-only tooling/configuration
- Local IDE configuration
- Generated temporary archives
- Playground/demo assets (unless explicitly justified)
- Unrelated repository files

## 8. CSS Architecture Preservation

The distribution process must perfectly preserve the existing conceptual architecture:

**Source Architecture:**
`Tokens → Foundation → Layout → Components → Utilities`

**Cascade Layers:**
`@layer reset, base, layout, components, utilities;`

Themes must remain part of the Token architecture (via custom properties) and must **not** become a separate cascade layer.

## 9. Feature Inclusion

### Theme Distribution
The package must include built-in themes out of the box:
- Default theme (`:root`)
- Dark theme (`[data-theme="dark"]`)

The consumer should not need a separate theme package, nor should they need a JavaScript theme runtime.

### Responsive Distribution
Responsive utilities must be included in the standard distribution. Consumers should not need to generate responsive classes dynamically. The breakpoints remain standard:
- `sm`: 640px
- `md`: 768px
- `lg`: 1024px

### Component Distribution
Current component CSS (such as the HEBRING Button) will be part of the main framework distribution. There are no separate component packages at this stage.

## 10. Package Properties

### Tree-Shaking
HEBRING's initial package architecture does **not** depend on JavaScript-style tree-shaking. The default distribution will be predictable and complete. If future modular CSS entry points become necessary, they will be introduced as a separate architecture decision.

### Versioning
Package versioning will strictly follow semantic versioning principles.

### File Extensions
The architecture favors standard CSS artifacts: `.css`. We do not introduce `.scss`, `.less`, CSS-in-JS, or generated JS runtime artifacts unless a future architecture decision explicitly requires them.

### Package Size
The architecture avoids unnecessary files and duplicated CSS. However, **readability, source accessibility, and predictable consumption** take absolute priority over premature micro-optimization.

### Build Tool Independence
The package architecture describes **WHAT** is distributed. It is not tied to Vite, Rollup, esbuild, PostCSS, or Lightning CSS. The tools used to generate the distribution artifacts are a separate implementation detail (Phase 10.3).

## 11. Future Extensibility

Future versions of HEBRING may introduce:
- Additional built-in themes
- Additional components
- Additional distribution artifacts
- Modular CSS entry points

However, none of these should be introduced prematurely. The initial package architecture remains lean, transparent, and focused on the core CSS framework.
